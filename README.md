# 服装门店与网店智能运营多 Agent 助手

> 把「服装图像分类模型」和「网店评论分析模型」两个确定性模型封装成 LLM 可调用的工具，  
> 用状态机编排「图像归档 → 标签归一 → 评论洞察 → 运营建议」业务闭环，  
> 并用评测集、结构化约束与人工确认机制做可信治理。
>
> 核心原则：**LLM 负责理解与编排，模型负责判定，人工保留确认权。**

---

## 一、快速开始

```bash
cd 服装店Agent
pip install -r requirements.txt

python run.py init      # 生成演示数据（12 商品 / 30 评论 / 标签库 / 评测集 / 样例图）
python run.py serve     # 终端 A：启动两个确定性模型服务（8801 / 8802）
python run.py chat      # 终端 B：自然语言跑完整闭环
python run.py eval      # 终端 B：评测回归
```

> `serve` 需常驻。`chat / classify / eval` 依赖它；未启动时会打印健康检查失败并提示。

### 接入真实大模型（可选）

```bash
export LLM_API_KEY=sk-xxx
export LLM_BASE_URL=https://api.deepseek.com/v1     # 或 OpenAI / 通义千问等兼容端点
export LLM_MODEL=deepseek-chat
python run.py chat "连衣裙差评集中在尺码，给我点建议"
```

未配置 `LLM_API_KEY` 时自动降级为 `rule-based-offline` 编排器（关键词路由 + 规则合成），  
**行为与真实 LLM 走同一套上下文/工具协议**，因此离线也能演示与做回归测试；  
此时所有报告都会标注 `编排后端=rule-based-offline`，不会把降级结果伪装成大模型能力。

## 四、三个版本的迭代逻辑

### V1 单 Agent 工具化 —— `python run.py classify`

**问题**：老板不会直接调 API。  
**做法**：用 Function Calling 把两个模型封装成工具，实现「上传图片→返回标签」「导入评论→返回多标签情感」。  
**关键设计**：工具参数白名单（`sanitize_args`），阻断提示注入塞入 `system`/`prompt` 等越权字段；每次调用留 `ToolCallRecord`，供回归比对参数稳定性。

### V2 多 Agent 业务闭环 —— `python run.py chat`

**问题**：单 Agent 只能回答单点问题，跨模块要手工切换。  
**做法**：拆为图像归档 / 评论洞察 / 运营建议三个 Agent，用显式状态机编排  
「图片归档 → 标签归一 → 评论按商品·品类聚合 → 生成选品/售后建议」。  
**关键设计**：

- 状态机只管路由与数据依赖，**不含业务判断**，节点可独立单测；
- 每轮把已取回数据回灌上下文（`_absorb`），让 `query_comments` 的结果真正流向 `analyze_comments`；
- 工具结果与评论**按 comment_id 严格对齐**，不做顺序假设。

### V3 评测与可信治理 —— `python run.py eval`

**问题**：LLM 会乱归纳标签和评论主题，且会编造结论。  
**做法**：

1. **结构化约束**：`Advice` 校验器强制 `tool_refs`/`evidence_ids` 至少一项，否则直接拒绝生成；
2. **评测集回归**：12 条人工标注用例，覆盖意图路由、标签归一、主题召回、证据闭环、参数安全；
3. **置信度分流**：低置信标签、单证据主题、低置信建议一律转人工确认队列；
4. **人工修正回流**：确认结果写入 `var/human_corrected_samples.jsonl`，作为 few-shot 与下一轮回归的输入；
5. **幻觉闭环校验**：逐条核对建议/主题引用的评论 id 是否真实存在于本轮分析集合。

## 五、两个确定性模型服务

| 服务                            | 端口   | 对应模型                              | 无权重时的降级后端                                    |
| ----------------------------- | ---- | --------------------------------- | -------------------------------------------- |
| `services/image_service.py`   | 8801 | ResNet50 + TorchVision 迁移学习       | `prototype-fallback`：色彩直方图 + 几何特征 → 分块加权最近原型 |
| `services/comment_service.py` | 8802 | BERT + CNN + Attention，Focal Loss | `lexicon-baseline`：领域词典 + 否定线索规则             |

两者接口契约完全一致，**Agent 层与状态机代码无需改动即可切换**。  
`/health` 会明确回报当前后端，报告里也会标注，**不会把降级结果当成真实模型指标**。

训练/校准：

```bash
python run.py train image --data data/train_images --epochs 8 --target-acc 0.60
python run.py train comment --gamma 2.0 --alpha 0.25 --threshold 0.30
```

`train image` 内置 **Early Stopping + 学习率衰减**，且 `best_acc < --target-acc` 时**直接中止**——  
不允许用不达标模型覆盖线上原型库。导出到 `var/` 后，服务重启即自动切换后端。

## 六·一、图像分类：后端选择与能力边界

图像服务支持 5 个后端，**按对真实商品照片的实际效果排序**自动选择（权重文件放好即生效）：

```
prototype-nn  >  siglip2  >  resnet50  >  fashion-cnn  >  untrained
```

| 后端             | 触发条件                      | 4 张实拍图     | 官方测试集     | 角色                       |
| -------------- | ------------------------- | ---------- | --------- | ------------------------ |
| `prototype-nn` | `var/image_classes.json`  | **全部判对 ✓** | —         | **主判定**，从真实照片学特征中心       |
| `siglip2`      | `var/siglip_fashion/` 有权重 | 全部判错 ✗     | 91.8%（公开） | **交叉验证信号**               |
| `resnet50`     | `var/resnet50_fashion.pt` | 取决于训练      | 取决于训练     | 自训练 ResNet50 TorchScript |
| `fashion-cnn`  | `var/fashion_cnn.pt`      | 全部判错 ✗     | 86.7%     | 模型层评测工具                  |
| `untrained`    | 都没有                       | 空结果        | —         | 明确低置信，全转人工               |

### ⚠️ 域差实测：一个反直觉但重要的结论

我把 HuggingFace 的 `Fashion-Mnist-SigLIP2`（公开指标 **91.8%**）下下来实测，

结果在**真实商品照片上是全部判错** —— 四张全部误判为「单肩包」，而且置信度高达 0.95~0.99。

做了三组对照实验定位根因：

| 实验                             | 结果         | 结论                 |
| ------------------------------ | ---------- | ------------------ |
| SigLIP2 跑 Fashion-MNIST **原图** | **全部判对 ✓** | 模型和加载链路完全正常        |
| SigLIP2 跑实拍图（224×224）          | 全部误判"单肩包"  | 域差                 |
| 实拍图先降采样到 28×28 灰度再放大           | 仍 全部判错     | 不是分辨率问题，是**图像域**问题 |

**根因**：SigLIP2 是在 Fashion-MNIST 的**白底平铺小图**上微调的，

它学到的是"小图中央的深色块 = 包"。真人穿着的照片缩到 224×224 后语义完全变了。

**这带来一个关键工程判断：公开指标高 ≠ 场景能用。**

所以后端优先级不按模型强弱排，而按**在自己业务数据上的实测效果**排——

`prototype-nn` 虽然没有任何公开论文背书，但在真实商品图上全部判对。


### 后端可信度注册表：装上不等于能用

既然"公开指标高 ≠ 场景能用"，那怎么知道哪个后端能信？

答案是**在业务数据上实测**，而不是看模型卡上的数字。

```bash
python run.py validate-backends --data data/train_images --min-acc 0.60
```

实测输出：

```
[validate] 样本 40 张，标签 4 类
[validate] 待测后端：siglip2, fashion-cnn, prototype-nn

[validate] siglip2        准确率   0.0%（无一正确）  ✗ 不采信
             - 001.png(大衣): 判为 单肩包
             - 001.png(毛衣): 判为 单肩包
             - 001.png(西裤): 判为 单肩包
             - 001.png(连衣裙): 判为 单肩包

[validate] fashion-cnn    准确率   0.0%（无一正确）  ✗ 不采信
[validate] prototype-nn   准确率 100.0%（全部判对）  ✓ 采信

[validate] 可信度注册表已写入 -> var/backend_trust.json
[validate] 采信后端：['prototype-nn']
```

结果写入 `var/backend_trust.json`，**只有被采信的后端才允许参与交叉验证投票**。

这一步的价值：避免了"不可信后端制造假冲突"。  
如果让 siglip2 参与投票，它每次都判"单肩包"，会 100% 触发冲突，  
把本来正确的结论全打成"待人工确认"——**过度保守同样是问题**。  
不可信的后端应该被排除，而不是用来添乱。

### 高置信度的错误，比低置信度的错误更危险

SigLIP2 对实拍图给的是 **0.98 的"单肩包"**——如果直接采信，  
下游会拿着一份"看起来很确定但完全错误"的结论去生成运营建议。

因此引入**多后端交叉验证**（`_cross_check`）：

```
主后端(prototype-nn)  连衣裙 0.42 ──┐
                                    ├── 结论冲突 → 置信度打折 + 标记 need_confirm
辅助后端(siglip2)      单肩包 0.98 ─┘
```

- 两者 Top-1 **一致** → 置信度上调（互证，可信度更高）
- 两者 Top-1 **冲突** → 置信度 ×0.55 + `need_confirm=True`
- Agent 层的三条转人工条件（任一满足即不自动采信）：
  1. 标签归一置信度不足
  2. 分类置信度 < 0.70
  3. **多后端交叉验证结论冲突**

触发条件用 **Top-1 与 Top-2 的分差**（≥0.12 说明主后端有明确区分，它说了算；  
分差小说明主后端自己也在犹豫，此时交叉验证才真正有价值），  
而不是绝对相似度——后者在训练样本上恒为 1.0，毫无判别力。

最终实测（4 张实拍图，可信后端只有 prototype-nn）：

| 图片        | 预测    | 置信度   | 交叉验证         | 延迟    | 结论   |
| --------- | ----- | ----- | ------------ | ----- | ---- |
| dress_001 | 连衣裙 ✓ | 0.764 | 未触发（无可信辅助后端） | 168ms | 自动采信 |
| coat_002  | 大衣 ✓  | 0.746 | 未触发          | 11ms  | 自动采信 |
| knit_003  | 毛衣 ✓  | 0.732 | 未触发          | 11ms  | 自动采信 |
| pants_004 | 西裤 ✓  | 0.749 | 未触发          | 14ms  | 自动采信 |

延迟从 300ms 降到 11ms——因为不可信后端不再被加载。

## 八、开发中修掉的真实缺陷

1. **召回偏差**：评论库按上架时间排列，简单 `limit` 截断导致后上架品类「0 条反馈」，  
   下游据此输出错误结论。→ 改为**按品类轮转均衡采样**，并在工具返回中显式回报覆盖率。
2. **多轮工具调用不推进**：离线编排器每轮重新规划，导致 `query_comments` 重复调用、  
   `analyze_comments` 从不触发。→ 引入 live 上下文快照（`_absorb`），让编排依据结构化数据而非解析历史消息。
3. **截断破坏结构化数据**：工具返回 1836 字符被裁到 1500，JSON 解析失败被静默当成空结果。  
   → `_trim` 改为按条目裁剪并显式标注 `truncated_to_N_items`，不再产出坏 JSON。
4. **特征权重失效**：整体 L2 归一化让 6 维几何特征被 64 维色彩特征压制。  
   → 改为**分块归一化 + 加权余弦**。
5. **低置信阻塞整链路**：图像标签待确认会中断整条链路。→ 改为**标记而不阻塞**  
   （评论洞察依赖评论证据，不依赖图像标签），只在最终状态标 `needs_human`。
6. **证据重复**：`[i for t in goods for i in t.evidence_ids]` 导致同一评论多次出现。→ 去重保序。
7. **跨 Agent 重复取数**：`comment_insight` 与 `operation_advice` 各查一遍同一批评论/商品。  
   → 引入共享数据池 `_harvest`，实测工具调用从 6 次降到 4 次（`query_comments` 省 1 次、  
   `query_products` 省 1 次），建议产出不变。
8. **手搓几何先验冒充模型**：早期原型库按"裤/裙高、上装居中"等人工先验构造，  
   对真实商品照片（带背景、模特、构图各异）几乎全错。  
   → 改为**从真实图片学习特征中心**，并加**留一法交叉验证**输出真实泛化指标；  
   样本不足时明确提示"当前 acc 为训练集准确率，不具备泛化意义"。
9. **爬图库标签不可靠**：Pexels 静态 ID 下载的图与目录标签完全对不上  
   （"连衣裙"目录里是挂衣架的 T 恤、"大衣"目录里是连帽卫衣），用脏数据训练等于学噪声。  
   → 改用标签精确的公开基准数据集 Fashion-MNIST（官方 MIT 许可）。
10. **Windows 上 torch 不支持中文路径**：`torch.jit.save/load` 遇到含中文的路径  
    （如 `D:/Projects/服装店Agent/var`）会误报 `Parent directory does not exist`，ASCII 路径正常。  
    → 统一走 `_save_torchscript` / `_load_torchscript`：先写/读纯 ASCII 临时目录，再搬运。
11. **numpy 手写 CNN 反向传播梯度错误**：数值梯度检查相对误差 1.6（阈值 1e-3），  
    定位到 maxpool 的 argmax 回传与池化索引维度不一致。  
    → 放弃手写反向传播，改用 torch autograd（`services/fashion_mnist_model.py`），  
    从根上消除这类 bug——**自己造轮子的成本远超收益**。
