> 服装门店与网店智能运营多 Agent 助手 · 独立开发
>
> 我给我姐姐的服装店和网店做了一套智能运营系统。核心是把**服装图像分类**和**网店评论分析**两个模型封装成大模型可调用的工具，用状态机编排「图片归档 → 标签归一 → 评论洞察 → 运营建议」的业务闭环。

# 二、3 分钟完整讲述

## 2.1 起点：真实的业务痛点（30 秒）

> 先说动机。我姐姐开服装店，同时做网店。日常有三个很具体的痛：
>
> 1. **上新归档靠人工**：每件衣服拍完照要手动归类、录标签，款式一多就乱；
> 2. **评论读不过来**：网店评论量大，长尾问题（尺码偏小、色差、起球）埋在长评论里，店主很难及时发现；
> 3. **两个模型是孤岛**：我之前做过图像分类和评论分析两个模型，但业务人员不会直接调 API，模型能力根本用不起来。
>
> 所以这个项目的目标很明确：**让店主用自然语言完成「衣服归类 — 上架标签 — 评论分析 — 运营建议」的完整闭环**。

## 2.2 架构：一句话讲清职责边界（45 秒）

> 架构的核心原则是一句话：**LLM 负责理解与编排，模型负责判定，人工保留确认权**。
>
> ```
> ┌────────────────────────────────────┐
> 店主自然语言 ──▶│ LLM 编排层 │
> │ 意图路由·工具选择·参数生成·标签归一 │
> └──────────────┬─────────────────────┘
> │ Function Calling（参数白名单校验）
> ┌──────────────▼─────────────────────┐
> │ 工具层（确定性判定） │
> │ classify_image / analyze_comments │
> │ query_comments / query_products │
> └──────────────┬─────────────────────┘
> ┌──────────────▼─────────────────────┐
> 业务上下文 ────▶│ 商品表 · 标签库 · 评论库 │
> └──────────────┬─────────────────────┘
> ┌──────────────▼─────────────────────┐
> 可信治理 ◀────▶│ 置信度分流·人工确认·证据闭环校验 │
> └────────────────────────────────────┘
> ```
>
> 三个关键设计：
> - **模型结论必须走工具层**。LLM 不能自己说「这是连衣裙」——必须调 `classify_image` 拿到带置信度的结果。我用 Pydantic 做了结构化约束，LLM 的自由文本结论进不了下游。
> - **所有跨层数据走 Pydantic**。`Advice` 这个 schema 有一个校验器：**没有引用任何工具输出或评论证据的建议，直接拒绝生成**。这是硬约束，不是提示词里的君子协定。
> - **工具参数白名单**。LLM 可能被提示注入诱导传入 `system`、`prompt` 这类越权字段，我在工具层统一过滤掉，只放行声明过的参数。

## 2.3 迭代路径：讲清「为什么演进到这一步」（45 秒）

> 这个项目是分三个版本迭代的，每次迭代都是被真实问题逼出来的：
>
> **V1 单 Agent 工具化** —— 先解决「模型能力用不起来」。用 Function Calling 把两个模型封装成工具，能跑通「上传图片→返回标签」「导入评论→返回情感」。
>
> **V2 多 Agent 业务闭环** —— 用起来发现单 Agent 只能回答单点问题，跨模块还得手工切换。于是拆成图像归档、评论洞察、运营建议三个 Agent，用显式状态机编排。状态机本身**不含任何业务判断**，只管路由和数据依赖，所以节点能独立单测。
>
> **V3 评测与可信治理** —— 又发现 LLM 会乱归纳标签和评论主题，甚至会编造结论。于是加了评测集回归、结构化约束、置信度分流和人工确认回流。
>
> 这条演进线在面试里可以直接引用：**「我先做的是两个确定性模型，后来发现业务人员不会直接调 API，所以 V1 用 Function Calling 把模型工具化；V2 发现单 Agent 只能回答单点问题，就用多 Agent 状态机做业务闭环；V3 发现 LLM 会乱归纳标签和评论主题，就加评测集、结构化约束和人工确认，让 Agent 可归因、可迭代。」**

## 2.4 硬核细节：域差实验（60 秒，最能打动面试官的部分）

> 这里我想重点讲一个我踩过的坑，也是我认为这个项目最有价值的部分。
>
> 我把 HuggingFace 上一个公开的服装分类模型 `Fashion-Mnist-SigLIP2`（Apache-2.0，92.9M 参数）接进来。模型卡的指标是 **91.8% 准确率**，很漂亮对吧？
>
> 但拿我姐姐店里的真实商品照去测——**全部判错**。而且它不是模棱两可，是**以 0.95~0.99 的极高置信度给出完全错误的结论**，四张全部误判为「单肩包」。
>
> 我做了三组对照实验定位根因：
>
> | 实验 | 结果 | 结论 |
> |---|---|---|
> | 让它跑 Fashion-MNIST **原图** | **全部判对** | 模型和我的加载链路完全正常 |
> | 让它跑真实商品照 | 全部误判为「单肩包」 | 有问题 |
> | 先把商品照降采样到 28×28 灰度再放大 | 仍全部判错 | **不是分辨率问题，是图像域问题** |
>
> 根因清楚了：这个模型是在**白底平铺的小图**上微调的，它学到的是「小图中央有一块深色区域 = 包」。真人穿着的照片缩到 224×224 之后，这个特征就成立了，于是全部误判成包。
>
> 这件事给我两个认知：
>
> **第一，公开指标高不等于你的场景能用。** 所以我改了后端选择策略——不按模型强弱排，**按在自己业务数据上的实测效果排**。最终主判定用的是我自己训的原型 KNN，全部判对。
>
> **第二，高置信度的错误，比低置信度的错误更危险。** 低置信度错误会被我的人工确认机制拦住，但 0.98 置信度的错误会一路畅通，生成一份「看起来很确定但完全错误」的运营建议。
>
> 针对第二点，我加了两个机制：
>
> - **后端可信度注册表**：后端不是装上就能用，必须先在自己的业务数据上实测达标才被采信。实测下来 siglip2 是 0%、另一个模型 0%、我的原型 KNN 100%——**只有达标的才允许参与投票**。这一步还避免了「不可信后端制造假冲突」：如果让 siglip2 参与投票，它每次都判「单肩包」，会 100% 触发冲突，把本来正确的结论全打成「待人工确认」，过度保守同样是问题。
> - **多后端交叉验证**：主后端和可信辅助后端投票，一致就上调置信度，冲突就打折并标记转人工。
>
> 这个经历也让我意识到一件事：**我原本手搓了一套「按服饰常识构造的原型先验」来兜底，比如「裤子高、鞋子扁」。但对带背景、模特、构图各异的实拍图，它几乎全错。** 手搓的先验看起来很合理，但它让分类结论「看起来可信」却不可信。后来我改成从真实图片里学特征中心，并加了**留一法交叉验证**——样本不足时系统会明确说「当前 acc 是训练集准确率，不具备泛化意义」，而不是给一个漂亮的假数字。

# 四、追问应答（预判高频问题）

## Q1：你这不就是把模型包了个壳吗？跟普通的 API 封装有什么区别？

> 差别在三点，都是我实际踩出来的：
>
> 1. **LLM 不允许直接下判定结论**。品类、情感这些结论必须来自工具层的确定性模型。我用 Pydantic 的 `Advice` schema 做了硬约束——没有引用的建议根本生成不出来。这不是 prompt 里写「请不要编造」，是代码层面拒绝。
> 2. **工具参数白名单**。LLM 可能被提示注入诱导塞 `system`、`prompt` 参数，我在工具注册层统一过滤，只放行声明过的键。这条我专门写了评测用例。
> 3. **治理层是独立模块**。置信度分流、人工确认队列、人工修正回流、幻觉证据校验，这些跟业务逻辑解耦，换个业务场景可以整套复用。

## Q2：准确率 86.7% 和 91.8%，你用哪个？

> 都要看，**但它们量的不是同一件事**。
>
> 86.7% 是我自己训的 Fashion-MNIST 小型 CNN，在官方测试集 3000 张上的**泛化准确率**。
> 91.8% 是 SigLIP2 公开模型的官方指标，我实测在它自己的测试集上复现了。
>
> 但这两个**都不能代表我这个业务场景的效果**，因为它们是 28×28 灰度图、白底平铺小图的域。我在自己的真实商品照上实测：86.7% 那个是全部判错，91.8% 那个也是全部判错。
>
> 所以我后来加了一套**在自己的业务数据上验证后端**的机制，页面上显示的那个全部判对和 100% 才是这个场景真正的数字。

## Q3：你的分类器就 4 张图训练，能泛化吗？

> 不能，而且我的系统**明确告诉我不能**。
>
> 训练脚本在样本不足时会输出「每类仅 1 张样本，无法做交叉验证；当前 acc 为训练集准确率，不具备泛化意义」。我不给漂亮的假数字。
>
> 而且这 4 张图既在训练集也在测试里，所以那个 100% 是训练集准确率，**不是泛化能力**。真正的验证要等我补更多真实照片——每类 5-10 张起步，然后跑留一法交叉验证，那才是可用的泛化指标。
>
> 这也是我把「后端可信度验证」做成独立命令的原因：**它逼着系统定期用新数据重新校准自己**，而不是一直靠一套过期的假设运行。

## Q4：为什么用 AdminLTE 不自己写前端？

> 时间成本和收益不划算。AdminLTE 是 GitHub 4.2 万 star 的 MIT 协议后台模板，自带表格、图表、侧栏、卡片这些我要的组件，静态文件不需要构建。我把时间花在**接后端和做业务逻辑**上——7 个页面的交互、交叉验证徽章、证据链展示、可信度面板，这些是自己写的。
>
> 顺带一个实际的坑：这个模板的图标字体 CSS 引用的是 `fonts/bootstrap-icons.woff2` 子目录，我第一次下载时把字体放在了同级目录，页面所有图标都变成方块。而且 Windows 的 `mimetypes` 不认识 `.woff2`，返回 `application/octet-stream`，浏览器会直接拒绝加载。两个都得修。

## Q5：多 Agent 状态机具体解决什么？跟一个 Agent 有什么本质区别？

> 状态机本身不含业务判断，只管两件事：**路由**（这次该走哪些节点）和**数据依赖**（上一个节点产出的数据怎么传给下一个）。
>
> 拆开的好处是节点能独立单测，而且**数据可以跨节点复用**。我实测过：评论洞察节点已经取过一次评论，运营建议节点就不必重复调 `query_comments`，工具调用从 6 次降到 4 次。
>
> 另外共享状态让「低置信转人工」这种判断可以横跨节点——图像归档发现低置信标签，不需要阻塞后面的评论分析（评论分析依赖的是评论证据，不依赖图像标签），只标记、最后汇总成 `needs_human` 状态。

## Q6：这套东西现在真的能用吗？瓶颈在哪？

> 能用，前端 7 个页面全通，Agent 对话能跑完整闭环。
>
> 瓶颈我很清楚，就三处：
> 1. **图像分类的泛化能力**——每类 1 张图不够，这是最需要补数据的；
> 2. **评论分析还是词典基线**——真正的 BERT+CNN+Attention 混合模型和 Focal Loss 我写了训练接口和评估，但没有真实权重，当前是 `lexicon-baseline` 后端，服务会明确回报这一点；
> 3. **编排层目前是离线降级模式**——配了 `LLM_API_KEY` 会走真实大模型，没配就走规则路由器，行为走同一套工具协议。报告里会标注当前后端，不伪装成大模型能力。
>
> 这三条都是**明确标注的待办**，不是藏着的问题。

## Q7：如果让你继续做，优先做什么？

> 优先级很清楚：**先补真实数据，再谈换模型**。
>
> 具体的：用姐姐店里攒的真实商品照片建一个带标准标签的小数据集，每类 5-10 张起步，跑留一法交叉验证得到真实泛化指标。有了这个基线，才知道是「数据不够」还是「模型不行」——现在这两件事是混在一起的。
>
> 然后是评论模型上真权重。词典基线在长尾主题上召回有限，我已经把服务接口留好了，模型换进来 Agent 层不用改。
>
> 最后才是编排层接真实大模型。这块反而是最不急的，因为我的设计里 LLM 只做理解和编排，判定都在工具层——**LLM 强弱的影响面被刻意限制住了**。

## Q8：可信度验证这个机制，会不会显得你在回避用更强的模型？

> 我觉得恰恰相反，它是让更强模型**能被正确使用**的前提。
>
> SigLIP2 公开指标更高、参数量更大、理论上上限更高。它没用上，不是因为模型差，是因为**没有验证机制的话，它的错误会一路畅通**——0.98 置信度地生成错误建议，比 0.5 置信度地生成错误建议危害大得多。
>
> 有了验证机制，等我攒够真实照片、做域适配微调，SigLIP2 就能直接切进来被采信。反过来，如果我一开始就无脑采信它，这个项目现在就是「看起来很 AI，实际在误导店主」的状态。

# 五、可能被问到但项目里没有的（诚实回答的模板）

如果面试官问到你没做的东西，**直接承认 + 给出你的设计思路**，比硬扯好：

> 「这个我没做。我目前的做法是 X，原因是 Y。如果要支持 Z，我的方案是 A/B/C，但我没实际验证过，所以不敢说它一定work。」

具体几个大概率被问到的：

| 问题 | 诚实的回答 |
|---|---|
| 有没有做向量检索 / RAG？ | 「没有。我的检索是**结构化查询**（按品类/商品筛评论），不是语义检索。原因是我发现简单的 `limit` 截断会导致后上架品类一条评论都取不到，下游据此输出「该品类 0 条反馈」的错误结论——我改成了按品类轮转的均衡采样。语义检索能进一步解决长尾问题，但当前的召回问题用均衡采样就够了。」 |
| 有没有做过向量数据库？ | 「没有，用的是 CSV + JSONL + 内存索引。数据量是 30 条评论、12 个商品，引入向量库属于过度设计。如果是真实的网店数据量，我会先做检索层的召回评测再决定。」 |
| 怎么防 LLM 幻觉？ | 「三层。① 结论层：品类/情感这类判定必须走工具层，LLM 不能自己下结论。② 结构层：`Advice` schema 的校验器强制要求引用证据，无证据直接拒绝生成。③ 事后层：证据闭环校验——逐条核对建议引用的评论 id 是否真实存在于本轮分析集合，孤儿证据会被剔除。」 |
| 做过压力测试吗？ | 「没有。我的并发是单机的 `ThreadingHTTPServer`，压测意义有限。我知道工业级需要什么（服务发现、限流、熔断），但没在这个规模上做过度设计。」 |
| 有没有用 LangGraph / 之类的框架？ | 「没有，状态机是我自己写的，约 200 行。因为我需要它只做路由和数据依赖、不含业务判断，框架反而会引入额外抽象。**框架的价值在于省掉 80% 的重复劳动，我的场景里那 20% 恰恰是要展示的部分。**」 |
