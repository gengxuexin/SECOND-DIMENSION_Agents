# 服装门店与网店智能运营多 Agent 助手

**LLM 负责理解与编排 · 模型负责判定 · 人工保留确认权**

把「服装图像分类」和「网店评论分析」两个确定性模型封装成大模型可调用的工具，
用状态机编排「图像归档 → 标签归一 → 评论洞察 → 运营建议」业务闭环，
并用结构化约束、评测集与人工确认机制做可信治理。

`Python 4404 行` · `3 个 Agent` · `5 个工具` · `7 个前端页面` · `MIT License`

</div>

---

## 这是什么

服装店/网店运营的三个真实痛点，本项目逐个解决：

| 痛点 | 方案 |
|---|---|
| 上新归档全靠人工，款式一多标签就乱 | `classify_image` 工具 + 标签归一，一句话批量归档 |
| 评论读不过来，长尾问题（尺码/色差/起球）被淹没 | `analyze_comments` 逐条打分 → 按品类聚合主题 → 每条主题带证据评论 id |
| 模型是孤岛，业务人员不会调 API | Function Calling 把模型封装成工具，自然语言即可驱动 |

## 快速开始

```bash
git clone <repo-url> && cd 服装店Agent
pip install -r requirements.txt

python scripts/download_fashion_mnist.py    # 下载数据集（31MB，自动校验完整性）
python run.py init                          # 生成演示数据

python run.py serve      # 终端 A：启动两个模型服务（8801 / 8802）
python run.py web        # 终端 B：启动 Web 前端 → http://127.0.0.1:8080
```

**接真实大模型**（可选，不配也能跑）：

```bash
export LLM_API_KEY=sk-xxx
export LLM_BASE_URL=https://api.deepseek.com/v1
export LLM_MODEL=deepseek-chat
```

未配置 API Key 时自动降级为 `rule-based-offline` 编排器，
**行为走同一套工具协议**，所有报告标注当前后端——不把降级结果伪装成大模型能力。

## 核心设计

### 1. 结论必须走工具层，LLM 不许自己下判定

品类是什么、评论是好评差评，这些**只能**来自确定性模型。
所有跨层数据走 Pydantic 结构化约束，`Advice` schema 带一个校验器：

> **没有引用任何工具输出或评论证据的建议，直接拒绝生成。**

这是代码层面的硬约束，不是提示词里的君子协定。

### 2. 工具参数白名单

LLM 可能被提示注入诱导传入 `system`、`prompt` 等越权字段。
工具注册层统一过滤，只放行声明过的键——有专门的评测用例覆盖。

### 3. 后端可信度注册表：装上不等于能用

本项目接入了 HuggingFace 上公开指标 **91.8%** 的服装分类模型 `Fashion-Mnist-SigLIP2`。
拿真实商品照实测：**全部判错，且以 0.95~0.99 的极高置信度给出完全错误的结论**。

三组对照实验定位根因：

| 实验 | 结果 | 结论 |
|---|---|---|
| 让它跑 Fashion-MNIST **原图** | **全部判对 ✓** | 模型与加载链路完全正常 |
| 让它跑真实商品照 | 全部误判为「单肩包」 | 有问题 |
| 先降采样到 28×28 灰度再放大 | 仍全部判错 | **不是分辨率问题，是图像域问题** |

根因：它在**白底平铺小图**上微调，学到「小图中央深色块 = 包」。

由此得到两条工程判断：

- **公开指标高 ≠ 你的场景能用** → 后端优先级按**业务数据实测效果**排，不按模型强弱排
- **高置信度的错误比低置信度的错误更危险** → 多后端交叉验证，冲突即打折转人工

```bash
python run.py validate-backends --data data/train_images --min-acc 0.60
```

```
[validate] siglip2        准确率   0.0%（无一正确）  ✗ 不采信
[validate] fashion-cnn    准确率   0.0%（无一正确）  ✗ 不采信
[validate] prototype-nn   准确率 100.0%（全部判对）  ✓ 采信
```

**只有通过业务数据验证的后端才允许参与决策投票**——
否则不可信后端会制造 100% 假冲突，把正确结论全打成「待人工确认」。

## 开发中修掉的真实缺陷

这些都是实际跑出来才发现的，不是设想：

1. **召回偏差**：评论库按上架时间排列，简单 `limit` 截断导致后上架品类「0 条反馈」，
   下游据此输出错误结论 → 改为**按品类轮转的均衡采样**
2. **多轮工具调用不推进**：离线编排器每轮重新规划，`query_comments` 重复调用而
   `analyze_comments` 从不触发 → 引入 live 上下文快照
3. **截断破坏结构化数据**：工具返回 1836 字符被裁到 1500，JSON 解析失败被静默当成空结果
   → `_trim` 改为按条目裁剪并显式标注
4. **特征权重失效**：整体 L2 归一化让 6 维几何特征被 64 维色彩特征压制
   → 分块归一化 + 加权余弦
5. **低置信阻塞整链路**：图像标签待确认会中断全链路 → 改为**标记而不阻塞**
6. **跨 Agent 重复取数**：两个 Agent 各查一遍同一批数据 → 共享数据池，工具调用 6→4 次
7. **手搓几何先验冒充模型**：早期按服饰常识构造原型，对实拍图几乎全错
   → 改为从真实图片学习特征中心 + 留一法交叉验证
8. **爬图库标签不可靠**：静态 ID 下载的图与目录标签完全对不上 → 改用标签精确的公开基准数据集
9. **Windows 上 torch 不支持中文路径**：`torch.jit.save` 遇到含中文路径误报
   「父目录不存在」→ 先写 ASCII 临时目录再搬运
10. **numpy 手写 CNN 反向传播梯度错误**：数值梯度检查相对误差 1.6（阈值 1e-3）
    → 放弃手写反向传播，改用 torch autograd
11. **图标字体全部显示为方块**：CSS 引用 `fonts/` 子目录但字体放在同级目录 +
    Windows `mimetypes` 不认识 `.woff2` → 对齐路径 + 显式 MIME 映射

## 已知边界

诚实列出当前限制：

- **图像分类泛化不足**：每类仅 1 张样本，全部判对是训练集准确率。系统已在
  `validate-backends` 和训练脚本中明确标注，不伪装成泛化能力
- **评论分析是词典基线**：真实 BERT+CNN+Attention 混合模型有训练接口与评估，
  但无真实权重，服务会明确回报 `lexicon-baseline` 后端
- **编排层默认离线降级**：配置 API Key 后走真实大模型，未配置走规则路由器
- **未做向量检索/向量库**：当前检索是结构化查询（按品类/商品筛评论），
  数据量 30 条评论 + 12 商品，引入向量库属于过度设计
- **无压测**：单机 `ThreadingHTTPServer`，未做并发性能验证
