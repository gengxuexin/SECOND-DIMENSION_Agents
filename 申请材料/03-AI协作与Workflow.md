# AI Coding 工具与 Agent Workflow 说明

> 申请材料第 3 项。这份文档说明我**实际怎么用 AI 干活**——
> 不是罗列工具，而是讲清楚一套可复用的协作方式，以及我如何保证 AI 的产出可信。

---

## 一、工具栈

| 工具 | 用途 | 我用它做什么 |
|---|---|---|
| **WorkBuddy（AI Agent）** | 主力 | 需求拆解、架构设计、编码实现、调试、代码审查、文档生成、截图验证 |
| **VSCode + JetBrains PyCharm** | IDE | 阅读与微调 AI 产出的代码、断点调试、Git 管理 |
| **Git** | 版本控制 | 提交历史即开发轨迹；每次改动可回溯 |
| **Edge / Chrome 无头模式** | 验证工具 | `--headless --screenshot` 截图，验证前端真实渲染效果 |
| **curl / Python urllib** | 接口验证 | 直接打 API 验证真实返回，而不是相信"应该没问题" |

> **说明**：Claude Code / Cursor 等工具我用过，但本项目的核心协作是在
> WorkBuddy 这个 Agent 环境里完成的，因为它支持**长任务 + 持久化工作记忆**——
> 跨会话记住之前修过哪些坑、为什么那么设计。

## 二、我的 Agent Workflow（核心方法论）

### 阶段 1：需求 → 可验证的任务清单

拿到需求先不写代码，而是拆成**可独立验证**的任务，每个任务有明确的验收标准。

以「做个前端」这个需求为例，我的拆解是：

```
1. 网络连通性确认（GitHub / npm registry / 镜像源速度）
2. 候选开源前端调研与选型（对比 star / license / 技术栈 / 是否免构建）
3. 克隆 + 精简（40M → 4.5M，只留运行时必需）
4. 依赖本地化（消除 CDN 依赖）
5. 后端 API 层设计
6. 页面实现
7. 逐页验证（HTTP 200 + 元素存在性）
8. 真实浏览器截图验证
```

**关键**：每一步都能用一条命令验证做对没做对。

### 阶段 2：实现 → 每步立即验证

**不写完一大坨再测**，而是写一小块、跑一次、看输出。

本项目的真实节奏：

```
改特征提取器 → 立刻跑 4 张真图分类 → 看 Top-1 是否正确
改标签库 → 立刻跑 normalize_tag 看归一结果
改状态机 → 立刻跑 run.py advice 看工具调用次数
改前端 → 立刻 curl 静态资源 → 再截图
```

这样做的好处：**问题在最小范围内暴露**，不会累积成"到底哪一步开始错的"。

### 阶段 3：遇到问题 → 先定位，再动手

不猜、不乱试。**先做对照实验区分"代码问题"和"环境/数据问题"**。

本项目里最典型的一次（SigLIP2 实测全部判错）：

```
假设 A：我的调用代码写错了
 → 对照实验：让它跑 Fashion-MNIST 原图 → 全部判对 ✓ 排除 A

假设 B：图片预处理不对
 → 对照实验：先降采样到 28×28 灰度再放大 → 仍全部判错 排除 B

假设 C：这就是域差
 → 结论成立：模型学的是"白底平铺小图"的特征
```

**三组对照实验**，把"我不知道哪错了"变成"我知道为什么错"。
这个过程完全是我和 AI 协作完成的——AI 负责提出假设和设计实验，我负责判断实验设计是否严谨。

### 阶段 4：AI 产出必须过"验证关"

**AI 说写完了 ≠ 写完了。** 我对每一类产出都定义了验收方式：

| 产出类型 | 验收方式 | 拒绝标准 |
|---|---|---|
| Python 代码 | 跑单元测试 + 真实命令 | 测试失败或输出与预期不符 |
| API 接口 | curl 打真实地址 | 非 200 或返回结构不对 |
| 前端页面 | HTTP 200 + 元素存在性 + **无头浏览器截图** | 元素缺失、样式错乱、图标变方块 |
| 模型指标 | 跑评测命令 | 数字对不上就重新跑 |
| 文档 | 逐条核对引用数字 | **文档里的每个数字都要能当场复现** |

**最关键的一条**：文档里引用的每个数字，我都会跑命令核对一遍。
本项目介绍文档写完后核对出 2 处偏差（文件数、延迟），全部修正。

### 阶段 5：把 AI 的产出沉淀成"项目自己的知识"

每次会话结束，工作记忆文件记录三件事：

```markdown
## 本次做了什么
（可复现的事实，不记流水账）

## 修掉了哪些真实缺陷 + 为什么
（问题现象 → 根因 → 修法 → 验证方式）
→ 这部分后来直接变成 README 里「开发中修掉的真实缺陷」章节
→ 也是面试时最有说服力的素材

## 用户偏好与约定
（如"下载到 D 盘"、"先做 demo 别凑数据量"、"需要具体操作步骤文档"）
```

这样下次会话 AI 不用重新问我项目背景，也知道我踩过哪些坑**不能重犯**。

## 三、我和 AI 的分工

这是我认为最该说清楚的一点：**AI 不是替我写代码，是替我做"信息搬运"和"穷举排查"。**

| 环节 | 谁做 | 例子 |
|---|---|---|
| 需求理解、业务建模 | **我** | 决定"图像归档→评论洞察→运营建议"三段式怎么切 |
| 技术选型 | 我定标准，AI 调研 | 标准：许可证干净、能跑、不引依赖过重 |
| 架构设计 | **我** | 决定"状态机只管路由不管业务判断"这条原则 |
| 代码实现 | AI 主力，我审 | 4404 行里大部分是 AI 写的 |
| **定位 Bug** | **我定假设，AI 跑实验** | 域差三组对照实验 |
| **判断哪些不能信** | **我** | 决定"公开 91.8% 的模型在实拍图上不可用" |
| 文档撰写 | AI 写，我核数字 | 每个数字跑命令核对 |
| 演示准备 | **我** | 决定演示顺序和话术 |

**最能体现人机分工的例子**：SigLIP2 那个决策。

AI 可以告诉我"这个模型指标 91.8%，建议使用"——这是纯信息搬运。
但**决定不用它**，是因为我在自己数据上测出了 全部判错。
如果我不做那三次验证，这个项目就会变成"看起来很 AI，实际在误导店主"。

## 四、AI 使用强度的真实数据

以本项目（服装店多 Agent）的开发过程为例：

| 指标 | 数值 | 说明 |
|---|---|---|
| 开发周期 | **2 天**（2026-10-20 ~ 10-21） | 从需求到可运行 + 可演示 + 文档齐全 |
| 代码产出 | 4404 行 Python + 675 行 JS + 112 行 CSS | 全部由 AI 主力实现 |
| AI 交互轮次 | **100+ 轮** | 含大量"改→跑→看→再改"的验证循环 |
| 文档产出 | 7 份 Markdown（约 25,000 字） | README / 操作手册 / 面试介绍 / 讲稿 / 下载清单等 |
| 自主调试轮次 | 30+ 次 | 全部由 AI 主动执行验证命令并根据输出迭代 |
| 人工介入点 | 约 15 次 | 集中在：选型决策、方向调整、真实图片提供、下载模型 |

### 我关注的不是"用了多少 AI"，而是这个比值

**如果 AI 一轮就写对，说明我的需求描述和验收标准不够清晰。**
本项目里 30+ 次自主调试，绝大多数是**我的验收标准把 AI 的"看起来对"挡下来的**：

- AI 说「特征提取已优化」→ 我要求跑 4 张真图看 Top-1 → 发现只有一张判对
- AI 说「训练完成，准确率 1.0」→ 我要求看留一法交叉验证 → 发现样本只有 1 张，泛化不可信
- AI 说「模型加载成功」→ 我截图看页面 → 发现图标全是方块（字体路径 + MIME 两个坑）
- AI 说「文档已写好」→ 我逐条核对数字 → 发现 2 处与实测不符

**这 4 个例子，就是"人工验收标准"比"AI 自报完成"更可靠的直接证据。**

## 五、可复用的 Prompt 模式

我在实践中沉淀了几种效果好的 prompt 结构：

### 1. 约束式（用于防止 AI 越界）

> 「用 X 方案，**别自己写**」
> 「**必须**先做对照实验排除假设 A、B，再下结论」
> 「**不预置、不伪造**这个数字」

### 2. 验收式（用于让 AI 自证）

> 「写完跑一遍 X 命令，把输出贴出来」
> 「数字要能当场复现」
> 「所有引用数字逐条核对」

### 3. 上下文式（用于长任务续接）

> 「读一下项目记忆文件，知道之前踩过哪些坑」
> 「这个坑之前修过，别重犯」

### 4. 角色分离式（用于避免"AI 自说自话"）

> 「你先假设是 A 原因，设计一个能排除它的实验」
> 「**别猜**，先定位」

**反面示例**（我踩过的）：

> ❌「帮我优化一下图像分类准确率」
> → AI 会给你一堆通用建议，甚至自己发明一些没根据的"优化"
>
> ✅「现在的分类器在 4 张真实商品图上只对 1 张。
> 先跑这 4 张看 Top-1 是什么，再判断是特征问题还是数据问题，
> 修完同样跑这 4 张对比。**不要引入我没要求的新框架。**」
> → AI 会真的去跑、去对比、给出可验证的结论

## 六、AI 没能替我做的事（也是我的价值所在）

诚实地列出来，这些是 AI 目前做不到、必须人来判断的：

| 判断 | 为什么 AI 做不了 |
|---|---|
| **决定不用 91.8% 的模型** | 需要先接受"实测全部判错"这个反直觉事实，再推翻已有的技术选型 |
| **区分"高置信度错误"和"低置信度错误"的风险差异** | 这是业务风险判断，不是技术判断 |
| **判断"全部判对但样本只有 1 张"这个数字能不能对外说** | 需要理解"训练准确率 vs 泛化能力"在真实场景的含义 |
| **决定把哪些边界写进文档** | 需要预判面试官/用户会在哪里质疑我 |
| **判断"什么时候该停手"** | AI 会一直尝试修到"看起来能跑"，但域差是改不动的，要承认并换路径 |
